# ADR-004: 整体余量维持"距下次封顶"语义（多窗口百分比取 min）

- 状态：已接受（2026-08-12，架构复盘质询轮 3）
- 关联：[[0001-hidden-webview2-on-demand]]、[[0002-credential-store-marker-only]]、[[0003-auth-expiry-notification]]、[[glossary]]

## 背景

`OverallPercent` 现状 = ChatGPT 剩余% 与 Go 三个窗口（5h / 周 / 月）剩余% 取最小值，50/30/10
告警与图标颜色均作用在该最小值上。质询发现其语义缺陷：**跨重置周期的窗口百分比不可比**——
5h 窗口（每 5 小时重置）几乎永远是聚合结果的常数主导项，而它恰好是后果最轻的约束（等几小时
即恢复）；月窗口（30 天）的告急信息反而被淹没，数字随 5h 窗口一天多次波动。

但 min 具有不可替代的正确性：**任一窗口耗尽都会真实封顶**（Go 三窗口各管各的闸门，ChatGPT
主窗口用满即锁），因此 min 就是"距下一次封顶的距离"——对"我还能不能用"这个核心问题，
它是标准答案。

## 决策

- **维持 min 聚合**（代码不动），语义定位为"距下一次封顶的最紧闸门"，而非"整体健康度"。
- **不做**按重置时间加权的归一化（用户不可解释）、不做"告警层按重置时间过滤"的额外规则
  （见下"拒绝的方案"）。
- 在 tooltip/详情文案的既有呈现（分窗口独立展示各剩余%与重置时间）之外不新增内容——
  用户需要"每个闸门各剩多少"时已有窗口级明细可看。

## 拒绝的方案

- **B. 告警按重置时间过滤**：额外规则收益低（告警本就受"档位标记 + 回升 5% 缓冲"约束，
  频率有界），却增加心智负担，且"5h 窗口只剩 10% 却无通知"在用户视角反而像漏报。
- **C. 归一化为可用量×时间**：数值失去百分比直觉，无法向用户解释。

## 影响

- 正向：语义自洽、实现与呈现零改动；"距封顶距离"始终保守正确。
- 负向：已知代价接受——图标数值受 5h 窗口主导、日内波动大；月窗口告急信息在聚合值中
  被稀释，需靠窗口级明细观察。

## 验收标准

- `OverallPercent` 仍 = 各窗口剩余% 的 min（无代码变更）。
- tooltip / 详情窗继续展示各窗口独立剩余%与重置时间。
- 无新增聚合规则。
